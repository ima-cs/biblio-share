# Rapport de validation de Biblio-Share

Audit du 23 novembre 2026 sous Windows, avec JDK 17, Spring Boot 3.5.6, Spring Cloud 2025.0.0, Docker et Newman 6.2.3. Base de comparaison dans le dossier de travail `docs/tp-reference` : grille de première évaluation et TP V2, V3, V4, V5 et V6. Aucun cahier des charges Biblio-Share séparé ne figurait dans ce dossier.

Les statuts se réfèrent à la grille et aux preuves ci-dessous. Le barème de référence est d’un point par élément réalisé, d’un demi-point pour un élément partiel et de zéro pour un élément non réalisé.

## Exécution et diagnostic

- Le dernier `mvn verify` avec JDK 17 a donné **BUILD SUCCESS** en 1 min 27 s pour les huit modules. Maven a exécuté quatre tests Spring répartis entre Catalogue, Adhérents et Prêt. Le test Maven de Prêt utilise des doublures Feign et RabbitMQ. Les preuves d’intégration ci-dessus viennent de processus Java séparés et des API réelles. [Maven](logs/maven-exact.log)
- Newman 6.2.3 a exécuté 71 requêtes et 99 assertions sans échec. Les captures HTTP incluent les corps enregistrés par Newman. [Sortie Newman](logs/newman.log) · [requêtes et réponses](logs/postman-http.json)
- L’audit a utilisé des bases H2 fichier séparées pendant les redémarrages, avec des données de test créées par les API. Le dernier parcours nominal a chargé les trois bases H2 en mémoire définies dans Git. Les paramètres de résilience temporaires ont été injectés au démarrage des JVM et retirés après les essais.
- Le premier parcours Newman a commencé avant la propagation complète d’Eureka. Il exécutait aussi les requêtes de panne en mode nominal et interrogeait Mailpit avant la livraison SMTP. La collection conditionne les pannes à la variable d’exécution et attend le courriel avec un délai borné.
- La première tentative de reconstruire un JAR en cours d’exécution a rencontré un verrou Windows au repackaging. La compilation de validation a utilisé un dossier de sortie neuf. Des échecs intermédiaires dans le journal d’intégration correspondent à cette tentative, avant le redémarrage Catalogue sur le JAR reconstruit.
- Le code de notification utilise l’exchange RabbitMQ par défaut et la clé `notifications.email`. Les événements locaux sont publiés vers RabbitMQ après le commit métier, puis le listener envoie le mail. Notification expose son contrôle de santé local. Le service ne comporte pas d’endpoint SMTP de test.
- En cas de rupture après le commit métier, la publication, l’acquittement et l’envoi SMTP ont des garanties distinctes. Un échec d’envoi au broker est journalisé et peut perdre la notification. Après épuisement des tentatives SMTP, la politique RabbitMQ configurée rejette sans remise en file.

## Résultats des scénarios de transport et de résilience

- **Deux événements V5.** Consumer arrêté, la file durable contenait deux messages prêts, aucun non acquitté et zéro consommateur. Mailpit ne contenait aucun des deux courriels ciblés. Après redémarrage, le courriel de retard concernait l’emprunt 66 et le courriel de disponibilité l’ouvrage 65. La file est revenue à zéro message prêt et zéro non acquitté avec un consommateur.
- **Temps métier.** L’emprunt en retard a été créé via HTTP avec échéance au jour courant. Pendant un redémarrage de la seule JVM Prêt, le fuseau de démonstration a fait avancer sa date locale d’un jour. La détection a produit une amende, puis le rejeu zéro nouvelle amende. La JVM a été redémarrée avec son fuseau initial.
- **Refus d’amende impayée.** Le test a d’abord observé la suspension automatique, puis a levé temporairement la suspension distante via l’API interne du service pour isoler la vérification de l’amende locale. La création a renvoyé HTTP 409 tant que l’amende était impayée. Le paiement a renvoyé l’état PAYEE.
- **Broker et SMTP.** Les pannes ont été obtenues en rendant inaccessible au seul processus concerné son port RabbitMQ ou SMTP, tout en conservant les conteneurs du projet. La panne broker a conservé le résultat métier et journalisé l’échec après commit. La panne SMTP a produit un échec d’envoi sans courriel et un nouvel événement a été livré après restauration.
- **Deux cibles Feign.** Pour Catalogue et Adhérents, les appels ont enregistré Retry, CLOSED_TO_OPEN, refus NOT_PERMITTED, OPEN_TO_HALF_OPEN et HALF_OPEN_TO_CLOSED. Un nouvel emprunt exigeant la cible arrêtée a reçu HTTP 503. Le détail HTTP 200 a conservé les données locales et l’autre enrichissement.
- **Quota, concurrence et lecture lente.** Avec un appel par dix secondes, le premier détail était enrichi et le second local. Avec un permis Bulkhead et la JVM Adhérents momentanément suspendue, le deuxième appel a reçu HTTP 503 en 125 ms. Le premier a effectué un retry après un délai de lecture proche de 2 s et a terminé après restauration du service. Les valeurs normales ont été restaurées.
- **Périmètre restant.** Le port catalogue 8081 a été vérifié dans Git et le port 8181 à l’exécution. Le cas d’une réponse perdue juste après la prise de l’exemplaire côté Catalogue n’a pas été injecté. Le code conserve l’emprunt EN_ATTENTE pour rejeu avec le même jeton. Aucun endpoint HTTP d’envoi direct n’est prévu dans Notification.

## Rejouer la démonstration

1. Exécuter `mvn verify` à la racine avec le JDK 17. En cas de verrou Windows, utiliser `mvn verify -Dbiblio.build.directory=target/remise` et prendre les JAR sous `target/remise`.
2. Exécuter `docker compose up -d --wait`. Démarrer Eureka, puis Config Server avec l’URI Git de la branche `main`. Vérifier `GET /service-catalogue/default` sur 8888 avant les clients. Les commandes JAR et les ports figurent dans le [README](../../README.md).
3. Démarrer les cinq clients. Après les six inscriptions UP, lancer `npx.cmd newman@6.2.3 run postman/Biblio-Share.postman_collection.json`. Si une instance auditée écoute sur 8181, ajouter `--env-var catalogue=http://localhost:8181`.
4. Pour V5, garder RabbitMQ et Mailpit actifs. Arrêter Notification, retourner deux ouvrages réservés ou déclencher un retour réservé et une détection de retard. Observer la file durable dans RabbitMQ Management sur 15672, puis redémarrer Notification et observer les courriels sur 8025.
5. Pour V6, conserver un emprunt et un exemplaire disponible distinct. Arrêter un service distant à la fois, tester `GET /loans/{id}/details` et une nouvelle création, puis restaurer le service. Pour examiner les événements, ajouter au démarrage de Prêt `--management.endpoints.web.exposure.include=health,info,circuitbreakerevents,retryevents,bulkheadevents,ratelimiterevents`. Les chemins correspondants sont sous `/actuator`. Une base H2 fichier temporaire permet de conserver les données entre redémarrages. Les options de débit et de concurrence figurent dans [service-pret.properties](../../config-repo/service-pret.properties).
